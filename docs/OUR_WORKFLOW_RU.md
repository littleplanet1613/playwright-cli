# Как Playwright CLI входит в нашу связку Codex

Playwright CLI не заменяет `open-steps` и не заменяет Astra/Luna Orchestrator. Он даёт им **реальный браузерный способ проверить результат**.

## Роли в нашей схеме

### Astra/Luna Orchestrator

Оркестратор решает, кто что делает:

- `explorer` находит нужный код и сценарии;
- `worker` вносит ограниченную правку;
- `tester` проверяет результат;
- `researcher` сверяет внешнюю документацию;
- `reviewer` независимо ищет ошибки;
- root собирает всё вместе и даёт итог.

Для веб-задач Playwright CLI в первую очередь нужен роли `tester`.

## Что должен делать tester

После финальной правки `tester` может:

1. запустить или использовать уже запущенное локальное приложение;
2. открыть его через `playwright-cli`;
3. получить snapshot страницы;
4. пройти нужный пользовательский сценарий;
5. при необходимости проверить desktop и мобильный viewport;
6. сохранить скриншот или PDF как доказательство проблемы или результата;
7. вернуть точный отчёт: что проверено, что прошло, что сломалось.

Пример контракта для tester:

```text
Проверь только изменённый пользовательский сценарий через playwright-cli.
Используй localhost.
Не редактируй production-код.
Проверь desktop и мобильный viewport.
Верни шаги проверки, pass/fail и найденные проблемы.
```

## Open Steps

`open-steps` отвечает за качество и понятность завершения задачи.

Для веб-задачи правило такое:

- старый скриншот не считается доказательством после новой правки;
- успешная сборка сама по себе не доказывает, что интерфейс работает;
- browser-check должен выполняться после финального изменения, если он важен для заявленного результата;
- если свежей проверки не было, итог должен говорить `не проверено`, а не `готово`.

## Рекомендуемый рабочий цикл

```text
1. Пользователь ставит задачу
2. explorer находит нужный участок
3. worker меняет код
4. обычные тесты / сборка
5. tester открывает приложение через Playwright CLI
6. tester проходит реальный пользовательский сценарий
7. reviewer проверяет итоговый diff
8. root собирает факты
9. Open Steps формирует понятный статус
10. пользователь решает, делать ли merge/deploy
```

## Когда Playwright не нужен

Не надо запускать браузер автоматически для каждой мелочи.

Обычно Playwright не нужен, если изменение касается только:

- серверной функции без UI;
- текста в документации;
- внутреннего скрипта;
- конфигурации, которую можно надёжно проверить более коротким тестом;
- задачи, где браузер не добавляет нового доказательства.

Это помогает не тратить время и лимиты впустую.

## Когда Playwright особенно полезен

- формы и кнопки;
- адаптивная мобильная вёрстка;
- модальные окна;
- drag-and-drop;
- загрузка файлов;
- многошаговые пользовательские сценарии;
- ошибки, которые воспроизводятся только в браузере;
- проверка после UI-рефакторинга;
- регрессии Safari/Chrome-подобного поведения, которые можно приблизительно проверить через Chromium;
- визуальное подтверждение, что приложение реально открылось после сборки.

## Безопасные границы

Browser automation способна выполнять реальные действия от имени пользователя.

Поэтому без явного разрешения не выполнять:

- покупку или оплату;
- удаление данных;
- публикацию в production;
- отправку массовых писем или сообщений;
- изменение DNS, доступа, паролей и других чувствительных настроек;
- подтверждение необратимой формы;
- действия в личном аккаунте, которые меняют реальные данные, если для проверки можно использовать тестовый аккаунт или localhost.

Если сценарий доходит до последнего безопасного шага перед необратимым действием, этого достаточно для проверки. Дальше агент должен остановиться и попросить подтверждение.

## Пример хорошей задачи Codex

```text
Исправь мобильную форму создания записи.
Используй оркестратор: explorer пусть найдёт поток, worker внесёт минимальную правку,
tester после финальной правки проверит форму через playwright-cli на desktop и mobile,
reviewer независимо проверит diff.
Не деплой и не merge без моей команды.
В конце дай простой отчёт: что изменено и что реально проверено.
```

Так Playwright становится не отдельной игрушкой, а частью нормального конвейера проверки.
